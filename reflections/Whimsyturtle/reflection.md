# Agentic SE Reflections: Whimsyturtle

In [MP1](https://github.com/Whimsyturtle/CS3227-2610-MP1/blob/main/docs/Reflections.md#lessons-i-learnt), I proposed packaging effective prompts as reusable skills and maintaining a repository glossary. In MP2, I developed these ideas in [Arbiter, our app](../../docs/index.md), through [skill consolidation](../../logs/Whimsyturtle/001-skill-consolidation.md), which grouped related agent tasks into reusable workflows, and [documentation rules](../../logs/Whimsyturtle/008-deduplicate-documentation-and-code-comments.md), which gave each fact one authoritative home, including the glossary for domain terms. The discussion of **artifacts as the interface** in Week 3 emphasised that human-written artifacts should minimise miscommunication, while agent-produced artifacts should be easy to verify and use for decisions. For me, meeting that standard required a feedback loop: inspecting the agent's work, identifying why it fell short, revising the relevant instruction, then checking its behaviour on another task.

## How I Chose the Skills

I organised skills around **coherent tasks with checkable outcomes**, following Week 4's guidance to give each skill one job with explicit inputs and outputs. In the [development workflow](../../context/swe.md#feature-workflow), `write-plan` prepares the branch and implementation plan, including how acceptance criteria will be verified; `write-test` designs, writes and runs focused tests during implementation; and `review` verifies the full change. Folding branch setup into planning avoided a separate skill for a preparatory step, while keeping test creation separate from full review let me request either task independently. These boundaries made it clearer which skill to invoke and what evidence would show its work was complete. ([Log 001](../../logs/Whimsyturtle/001-skill-consolidation.md); [initial skill commit](https://github.com/CS3227-2610-MP2-Arbiter/CS3227-2610-MP2/commit/fe55feda9e4cfc6ede33366683c2e21cebecc8bd))

## Three Skills in Detail

### 1. `write-test`: Derive Expectations Before Inspecting Implementation

After finding the tests for creating and opening Arbiter's [workspace (shared data folder)](../../docs/Glossary.md) unsatisfactory, I revised [`write-test`](../../.codex/skills/write-test/SKILL.md) to derive expected outcomes from requirements and observable behaviour, apply **equivalence partitioning**, **boundary value analysis**, positive and negative tests, and relevant input combinations, then inspect implementation paths. This applies the distinction discussed in Week 2 between specification-based **black-box testing** and implementation-based **white-box testing**. Starting with the specification reduces the risk of tests agreeing with the implementation simply because both encode the same mistake. ([Log 010](../../logs/Whimsyturtle/010-rework-write-test-around-test-design-techniques.md); [skill revision](https://github.com/CS3227-2610-MP2-Arbiter/CS3227-2610-MP2/commit/9b8a9931f83a5538a1365838cb216f34e44aa56f))

Applying the revised skill added the missing test for reopening a workspace after moving its folder and uncovered a defect under the persistence design used then: opening a workspace succeeded even when its database file, `arbiter.db`, was missing. I authorised the production fix, after which the workspace tests passed. This gave me concrete evidence of **defect-finding power** and **requirements traceability**, two criteria from Week 2's test-case review checklist; a larger test suite alone would not necessarily have demonstrated either. ([Log 011](../../logs/Whimsyturtle/011-rewrite-workspace-tests-with-write-test.md))

The skill also requires the agent to preserve a test exposing a suspected defect and report it without changing production code. That boundary lets me inspect the failure before authorising a fix. ([Skill completion criteria](../../.codex/skills/write-test/SKILL.md); [logs 010](../../logs/Whimsyturtle/010-rework-write-test-around-test-design-techniques.md) and [011](../../logs/Whimsyturtle/011-rewrite-workspace-tests-with-write-test.md))

### 2. `review`: Turn a Repeated Defect into a Reusable Check

[`review`](../../.codex/skills/review/SKILL.md) checks a change against its requirements, inspects verification results, and reports findings and remaining human checks. During acceptance testing, I found that the GUI confirmation message for assigning annotation work was cut off with an ellipsis and recognised the same problem on the workspace owner's login screen, so I requested a skill change alongside the shared UI fix. The [resulting revision](https://github.com/CS3227-2610-MP2-Arbiter/CS3227-2610-MP2/commit/7690f738f85804d982dca87239e4104474e0517b) required checking that screen text remains fully visible even with the longest realistic messages. I did this as I wanted each correction to improve the next review and reduce repeated coaching. ([Log 022](../../logs/Whimsyturtle/022-assign-annotators-to-splits.md))

Nevertheless, that instruction still had limits: my acceptance testing found GUI tables shrinking until only their headers were visible in a small window after an agent review had missed the problem; subsequent work fixed scrolling across the app's screens and added a regression test for the label and rating configuration screen. That test failed on the previous scrolling code. Hence, the long-text check was useful but insufficient: the review also needed to check the layout at smaller window sizes. This showed me that the skill needed broader **usability** checks, a testing concern discussed in Week 2. ([Log 027](../../logs/Whimsyturtle/027-monitor-basic-project-progress.md))

I also needed `review` to report which checks actually ran, rather than just whether the build succeeded. During verification of Arbiter's export feature, the first build reused earlier results, so the agent forced a rerun. Some tests still could not run on Windows and were reported separately, making clear that a successful build did not mean every test had run and passed. This relates to Week 5's **verification completion** metric: the proportion of agent runs that execute all required checks. ([Log 026](../../logs/Whimsyturtle/026-export-csv-or-json-datasets-with-provenance.md))

### 3. `maintain-docs`: Control Which Facts the Agent Treats as Authoritative

[`maintain-docs`](../../.codex/skills/maintain-docs/SKILL.md) checks documentation against accepted behaviour and puts facts in their designated homes. After finding duplication across documentation and code comments, I established the [one-home rule](../../AGENTS.md#one-home-per-fact), then replaced the skill's separate list of where facts belonged with a reference to it. This applied **DRY** to the agent's context: duplicated requirements create opportunities for drift, even when every individual paragraph sounds plausible. ([Log 008](../../logs/Whimsyturtle/008-deduplicate-documentation-and-code-comments.md); [skill revision](https://github.com/CS3227-2610-MP2-Arbiter/CS3227-2610-MP2/commit/5992ce8759116679ce2b22376e9c8b467e529d83))

The agent raised contradictions for me to resolve, including the distinction between [disputed items (unsettled label disagreements) and unresolved items (no final answer yet)](../../docs/Glossary.md) and the separate restrictions on changing a project's taxonomy kind (single-label or numeric rating) and its available labels. Terminology mattered because it shaped the application's data model and the rules enforced by its services. This illustrated **human oversight**, as discussed in Week 5: the agent could identify inconsistent statements, but choosing the intended behaviour remained my responsibility. ([Log 008](../../logs/Whimsyturtle/008-deduplicate-documentation-and-code-comments.md))

The cleanup itself needed correction: its first pass lost unresolved questions about the data model and introduced incorrect wording about deletion rules. That experience qualified my preference for concise context. Shortening documents helps only if it preserves decisions, uncertainty and useful references; removing those would make future work harder to judge. ([Log 008](../../logs/Whimsyturtle/008-deduplicate-documentation-and-code-comments.md))

## Where I Exercised Engineering Judgement

With limited time, I asked the agent to rank scope cuts, then deferred image annotation with bounding boxes and detailed reports on annotator activity and label agreement, while retaining numeric ratings (`SCALE`) and export in both CSV and JSON. Its analysis helped me consider implementation effort and dependencies when selecting cuts; equal issue counts would not necessarily give us equal workloads. The agent also propagated the accepted decisions across the backlog. I found it useful for analysing options and applying decisions consistently, while deciding which complexity was justified remained my responsibility. ([Log 012](../../logs/Whimsyturtle/012-rank-v1-scope-cuts.md))

I also requested the Jackson library for reading and writing JSON and CSV, replacing or avoiding custom code for those formats. Reusing a library reduced the parsing and escaping logic we had to maintain, but did not remove our responsibility to test integration and failure behaviour. For example, a second review of Arbiter's export feature tried writing to a file that was open in Excel and exposed an unclear error that the first review had missed. ([Logs 009](../../logs/Whimsyturtle/009-resolve-review-comments-on-workspace-setup.md) and [026](../../logs/Whimsyturtle/026-export-csv-or-json-datasets-with-provenance.md))

The agent created extra work when it added bookkeeping or repeated instructions: I removed an unnecessary tester-name requirement and reversed log-organisation rules added to the workflow overview. I also changed the logs from repetitive turn summaries into task summaries preserving corrections and verification. **Traceability**, as discussed in Week 5, depends on retaining evidence that lets us reconstruct and explain what happened; verbosity alone does not provide it. ([Logs 001](../../logs/Whimsyturtle/001-skill-consolidation.md) and [002](../../logs/Whimsyturtle/002-log-organization.md))

## What I Would Change

My evaluation was mainly iterative and manual. Initial structural checks established that the skills were well formed, and later tasks showed useful outcomes, but these did not establish reliable triggering or quantify productivity gains. The discussion of agent testing in Week 4 distinguished testing standard project artifacts from testing the agent's behaviour; I would make that second layer more systematic. ([Logs 001](../../logs/Whimsyturtle/001-skill-consolidation.md), [010](../../logs/Whimsyturtle/010-rework-write-test-around-test-design-techniques.md) and [011](../../logs/Whimsyturtle/011-rewrite-workspace-tests-with-write-test.md))

I would keep a small regression dataset drawn from these failures: a test-only request exposing a production defect, a documentation contradiction, a screen with long text, and a review with cached or skipped checks. Following Week 4's guidance on invocation tests, I would test **explicit, implicit and contextual invocation**, plus **negative controls** that should not trigger a skill. Building on Weeks 4 and 5's guidance on graders, I would use deterministic checks for changed paths and executed commands, and human review for test quality and design appropriateness. Repeating cases across skill versions would give better evidence of improvement than one successful task.

I would retain the habit that proved most useful here: turn a concrete correction into a focused instruction, then inspect whether it changes later behaviour. Designing the agent's workflow made my judgement reusable, while reviewing its outputs kept me accountable for the result.
